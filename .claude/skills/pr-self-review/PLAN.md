# PR Self Review — план скила

Статус: **план, код не написан**. Дата: 2026-09-26.

Источник истины — этот файл. Реализация форка курса (`upstream/lesson-2-lab/skills`) разобрана
ниже как ещё один вход, а не как образец: часть её решений мы берём, часть отвергаем по
проверенным причинам.

---

## 1. Задача и где в ней подвох

Из задания: скил запускается перед открытием PR (автоматически) или вручную; проверяет все
открытые изменения; сопоставляет наши скилы с diff так, чтобы UI-скилы шли на UI-файлы, а
бекенд-архитектурные — на бекенд-файлы; **если найден хотя бы один critical finding — запретить
юзеру мержить эти изменения**.

Подвох в последнем пункте. «Запретить мержить» и «запретить Claude выполнить `git push`» — разные
вещи, и путать их опасно: получится гейт, который выглядит установленным, но ничего не держит.
Проверено по документации (источники в §13):

| Точка перехвата | Что реально ловит | Чем обходится |
|---|---|---|
| `PreToolUse` hook | только tool-call'ы **самого Claude** | `!`-префикс в промпте, собственный терминал, кнопка Merge на GitHub; **плюс хук fail-open при падении и при таймауте** |
| git `pre-push` hook | любой push из этого клона, включая ручной | `--no-verify`, `-c core.hooksPath=/dev/null`; нужно, чтобы каждый разработчик один раз включил `core.hooksPath` |
| GitHub required status check | **сам мерж, для всех** | админ, если правило не применено к админам |

Вывод, определяющий всю архитектуру: **запретить мерж способен только required status check на
GitHub**. Локальные хуки — это быстрая обратная связь, а не гейт. План строит три слоя и честно
подписывает, что каждый может и чего не может.

Отдельный факт про нашу машину: `gh` не установлен (`command -v gh` → пусто), PR открывается
через ссылку, которую печатает `git push`. Значит локально единственная реальная точка — `git push`.

## 3. Форк курса: что берём, что отвергаем

Форк (`.claude/skills/pr-self-review/`: `SKILL.md`, `routing.md`, `gate.md`, два скрипта) —
вдумчивая работа, и три его идеи мы берём целиком.

**Берём:**

| Идея форка | Почему берём |
|---|---|
| Скил — оркестратор, а не носитель знаний: роутит в существующие скилы | Ровно наша задача; дублировать ревью-знание в скиле означает вторую копию, которая разойдётся |
| Детерминированные гейты **до** LLM-проходов, fail-fast | Дешёвый и самый сильный сигнал; нет смысла жечь токены на дереве, которое не компилируется |
| Только добавленные/изменённые строки; никогда не блокировать за чужой легаси-код | Сильнейшее правило против ложных срабатываний. Совпадает и с Google: аппрувить, если изменение улучшает общее здоровье кода |
| Adversarial-проверка каждого CRITICAL перед блокировкой, с понижением, а не тихим выбросом | Один ложный блок учит команду обходить гейт |
| Закрытый каталог CRITICAL — блокирует только то, что в списке | Предсказуемость: разработчик заранее знает, за что его остановят |
| `diffHash`: PASS протухает, если дерево изменилось | Аккуратно закрывает дыру «отревьюил, потом дописал» |
| Подавление с **обязательной** причиной, которая печатается в отчёте | Подавления остаются видимыми, а не тихими |
| Хук сам ревью **не** запускает, только читает вердикт | Единственно верное решение: ревью дольше таймаута, а таймаут хука = fail-open |

**Отвергаем — с причиной:**

| Решение форка | Почему нет |
|---|---|
| `PreToolUse` подан как merge gate | Он не гейт. Ловит только команды Claude; `!`, свой терминал и кнопка Merge проходят мимо. Задание требует запретить **мерж** |
| `matcher: "Bash"` на каждый bash-вызов | Есть поле `if: "Bash(git push*)"` — сужает до нужных команд и само разбирает `&&`, `$()` и подстановку через переменную |
| `exit 2` для отказа | Документация рекомендует `exit 0` + `hookSpecificOutput.permissionDecision: "deny"` с причиной; верхнеуровневые `decision`/`reason` объявлены устаревшими |
| Парсинг JSON через `node -e` с `\|\| echo "ERR"` и allow на ERR | **Проверено на нашей машине:** `node` стоит через nvm и отсутствует в минимальном PATH (`env -i PATH=/usr/bin:/bin` → `NO node`), а `jq` и `shasum` есть в `/usr/bin`. То есть у нас этот скрипт молча деградирует в no-op. Берём `jq`; «не смог проверить» должно **не** означать «пропускаю» |
| Матчеры на `gh pr create` / `gh pr merge` | `gh` не установлен; мёртвый код. Оставляем как опциональную ветку ради переносимости, но основной локальный перехват — `git push` |
| Жёстко прошитая карта скилов | Ссылается на `frontend-architecture`, `vercel-react-best-practices`, `nodejs-best-practices`, которых у нас нет, и не знает наш `frontend-ui-architecture`. Отсутствующий скил = целый бакет не отревьюен при зелёном PASS |
| Своя шкала CRITICAL/HIGH/MEDIUM + слой маппинга | У нас уже есть контрактная шкала `CRITICAL/WARNING/SUGGESTION`, на которой построен сам продукт. Свой продукт — свой словарь, слой маппинга не нужен |
| `gate.md`: «depcruise не подключён» | Устарело: у нас `pnpm arch` работает и baseline вычищен в 0 |

## 4. Три слоя

```
Слой 1  PreToolUse hook        →  быстрое напоминание, ловит только Claude        [advisory]
Слой 2  git pre-push hook      →  ловит любой push из клона, в т.ч. ручной        [advisory]
Слой 3  GitHub required check  →  единственное, что реально запрещает мерж        [enforcing]
```

**Слой 1 — `PreToolUse`.** Регистрируется в `.claude/settings.json` с
`"if": "Bash(git push*)"`. Ревью не запускает: читает `.pr-self-review.json`, сверяет `diffHash`,
отдаёт `permissionDecision: "deny"` с причиной. Скрипт — на `jq`, без `node`. Если состояние
прочитать нельзя — **deny с текстом «гейт не смог провериться»**, а не allow. При этом помним:
падение или таймаут самого хука всё равно fail-open, поэтому слой 1 остаётся напоминанием.

*Нюанс:* хук можно объявить и во frontmatter самого скила, но он регистрируется только после
первой инвокации скила, поэтому для «всегда включено» нужен именно `settings.json`.

**Слой 2 — `pre-push`.** Файл в `.githooks/pre-push`, включается один раз:
`git config core.hooksPath .githooks`. Ловит ручной push из терминала — дыру, которой слой 1 не
видит. Обходится `--no-verify`; это нормально, слой 2 тоже advisory.

**Слой 3 — CI, единственный настоящий.** Workflow `.github/workflows/pr-self-review.yml` на
`pull_request` перезапускает гейт и падает при ≥1 подтверждённом CRITICAL. Делается required
status check в ruleset'е с expected source = GitHub Actions. Почему не статус через PAT: он
удовлетворяет проверку «any source», но его может выставить кто угодно с write-доступом, включая
самого автора PR — то есть это не гейт, а самоподпись.

Отдельно стоит знать: Anthropic'овский Managed Code Review сознательно завершает свой check-run с
`neutral`, чтобы **никогда** не блокировать мерж. Если позже подключим его — блокировать должен
наш job, разбирающий его вывод, а не он сам.

## 5. Как считается diff

```
BASE = git merge-base origin/main HEAD
```

«Все открытые изменения» = закоммиченное-но-не-влитое + staged + unstaged + untracked.
Ревьюятся **только добавленные/изменённые строки**.

Всегда пропускаем: `**/vendor/shared/**` (кроме проверки на рассинхрон копий),
`server/src/db/migrations/**`, lock-файлы, `node_modules/`, `dist/`, `.next/`, чистые `*.md`.

`.pr-self-review.json` добавляется в `.gitignore` (локальное состояние, у каждого своё).

## 6. Роутинг: diff → скилы

Один subagent на бакет, параллельно. По документации subagents **не наследуют** скилы родителя,
но поле `skills:` в их frontmatter инжектит полное тело скила — это и есть механизм, который
делает «UI-скилы на UI-файлы» настоящим, а не декларативным.

| Бакет | Пути | Скилы |
|---|---|---|
| **UI** | `client/**/*.{ts,tsx,css}` | `frontend-ui-architecture`, `react-best-practices`, `next-best-practices` |
| **Backend** | `server/**/*.ts`, `reviewer-core/**/*.ts` | `onion-architecture`, `fastify-best-practices`, `drizzle-orm-patterns`, `postgresql-table-design` |
| **Схема БД** | `server/src/db/schema/**` | `postgresql-table-design`, `drizzle-orm-patterns` |
| **Тесты** | `**/*.test.{ts,tsx}`, `e2e/**` | `react-testing-library` (UI), `TESTING.md` — только стиль, **никогда не блокирует** |
| **Сквозной** | любой изменённый `.ts`/`.tsx` | `typescript-expert`, `zod`, `security` |
| **Всегда** | — | `INSIGHTS.md` затронутых пакетов как дополнительные критерии |

**Preflight, которого у форка нет:** перед запуском проверяем, что каждый скил из таблицы
физически существует в `.claude/skills/`. Нет скила → прогон помечается `DEGRADED` и печатает,
какой бакет остался без ревью. Молча пропустить бакет и выдать зелёный PASS — худший исход.

Для маленьких диффов (≤3 файла, один бакет) fan-out не окупается — ревьюим инлайн.

## 7. Что блокирует

### 7.1 Детерминированные гейты (первыми, без токенов)

Для каждого затронутого пакета, в порядке; первый ненулевой выход → **BLOCKED**:

1. `typecheck`
2. `pnpm arch` (только `server`) — нарушение onion-правила уровня `error`
3. `test`
4. `client`: `next build` — если diff трогает `client/**`

**Правило-храповик:** перегенерировать `.dependency-cruiser-known-violations.json`, чтобы новое
нарушение прошло, — это само по себе CRITICAL. Baseline сейчас пустой; он может только оставаться
пустым или уменьшаться.

### 7.2 Закрытый каталог CRITICAL

Блокирует **только** то, что в списке; всё остальное — максимум WARNING.

**Бекенд**
- Нарушение onion-правила, помеченное `error` (I/O в `reviewer-core`; сервис, импортирующий
  конкретный адаптер; роут, лезущий в `src/adapters/`).
- Рассинхрон двух вендоренных копий `@devdigest/shared` для затронутого контракта.
- Невалидированный внешний вход через границу доверия: тело/квери роута без Zod; `JSON.parse`
  ответа LLM или payload'а джобы без схемы.

**UI**
- Нарушение правил хуков; сайд-эффект во время рендера; хранение того, что должно выводиться.
- Next-специфичное: специальный файл App Router (`page`/`layout`/`not-found`/`loading`/`template`)
  без `"use client"`, который импортирует из `@devdigest/ui` — см. §8, у нас это уже стреляло.

**Общее**
- Секрет/креды в диффе.
- Ошибка типов или падающий тест из §7.1.

### 7.3 Два независимых фильтра до блокировки

Взято из официального тулинга Anthropic, где это уже отлажено: `/security-review` отдаёт только
findings с уверенностью **≥8/10**, а плагин `code-review` отбрасывает всё ниже порога и оставляет
только high-confidence после валидации параллельными субагентами.

1. **Порог уверенности:** finding блокирует только при confidence ≥ 8/10.
2. **Adversarial-проход:** отдельный скептик получает задачу опровергнуть finding («правда ли вход
   контролируется атакующим? правда ли это изменённая строка? правда ли это нарушает правило?
   при сомнении — считать опровергнутым»). Выживший — блокирует. Опровергнутый — понижается до
   WARNING и **печатается как пониженный**, а не исчезает.

Подавление: `// pr-self-review-ignore: <причина>` на той же строке; причина обязательна и
попадает в отчёт («подавлено: N»).

Escape hatch обязателен, иначе гейт просто удалят (Johnson et al., ICSE 2013: главная причина, по
которой разработчики бросают статический анализ, — ложные срабатывания и шум). Локально —
`PR_SELF_REVIEW_OVERRIDE="причина"`; в CI — **метка на PR** (`gate:override`), а не переменная
окружения, потому что метку видно ревьюеру, а переменную нет.

## 8. Чего этот гейт структурно не поймает

Это раздел, которого у форка нет, и он основан на двух записях из нашего же `client/INSIGHTS.md`.

**Кейс 25.09 (вчерашний).** `not-found.tsx` без `"use client"` тянул barrel `@devdigest/ui`, а с
ним recharts, в серверный RSC-граф, и клал **каждый** роут с `Super expression must either be null
or a function`. При этом: `typecheck` — зелёный, 147 тестов vitest — зелёные, `next build` — зелёный
и даже пререндерил `/_not-found`. Проверено отдельно: `next build` + `next start` + запрос на
настоящий 404 тоже отдают корректную страницу. Падает **только** `next dev`.

**Кейс 21.09.** Панель предпросмотра, держащая один слот для мыши и клавиатуры: каждый тест по
отдельности зелёный, typecheck/vitest/build зелёные — сломанность видно только в браузере.

Вывод, который надо записать в сам скил: **гейт из typecheck + тестов + build сказал бы PASS обоим
этим багам.** Поэтому:

- если diff трогает специальные файлы `client/src/app/**` — гейт обязан либо выполнить runtime-шаг
  (поднять `next dev`, дёрнуть один валидный URL и один 404, проверить консоль), либо явно
  напечатать `runtime: not verified`;
- отчёт всегда заканчивается строкой о том, что именно осталось непроверенным, — тишина не должна
  читаться как «всё проверено».

## 9. Фазы

**Фаза 0 — спека.** `specs/2026-09-26-pr-self-review.md` (кросс-пакетная: `.claude/` + CI + все
четыре пакета), EARS-критерии, без путей и кода. Примеры:
- `WHEN` дифф содержит ≥1 подтверждённый CRITICAL, система `SHALL` завершить CI-джоб ненулевым кодом.
- `IF` скил из таблицы роутинга отсутствует на диске, `THEN` прогон `SHALL` сообщить `DEGRADED` и назвать бакет.
- `WHILE` дифф не менялся с момента последнего PASS, хук `SHALL` разрешать push без повторного ревью.

**Фаза 1 — baseline без скила.** По нашему же правилу (`.claude/INSIGHTS.md`, 25.09): скил пишется
против измеренного провала, а не против списка best practices. Гоняем процедуру руками на двух
диффах и записываем, что найдено/пропущено и сколько стоило.

**Фаза 2 — детерминированный слой.** `scripts/` (diff-hash, check-gate на `jq`), состояние,
`.gitignore`, слой 1. Полезен сам по себе, ещё без единого LLM-прохода.

**Фаза 3 — роутинг и ревью.** Таблица §6 + preflight существования скилов + fan-out субагентов с
`skills:` + нормализация к нашей контрактной шкале.

**Фаза 4 — фильтры и вердикт.** Порог ≥8/10, adversarial-проход, каталог §7.2, подавления, отчёт.

**Фаза 5 — enforcement.** `pre-push` (слой 2), workflow + required check в ruleset (слой 3),
метка-override.

**Фаза 6 — README скила** с таблицей источников и changelog, как у `frontend-ui-architecture` и
`onion-architecture`.

## 10. Как проверим, что он работает

Regression-фикстуры с известным правильным ответом — у нас их две, обе из этой недели:

| Фикстура | Ожидаемо |
|---|---|
| Вернуть `not-found.tsx` без `"use client"` | BLOCKED, и именно по правилу из §7.2 UI. Если PASS — гейт не поймал реальный баг, который положил приложение |
| Взять коммит `8217ab6` (доступность, 41 файл, чисто) | PASS. Ложный блок на чистом диффе — провал |
| Внести нарушение onion-правила в `server/src/modules/*/routes.ts` | BLOCKED на `pnpm arch`, **без** LLM-прохода |
| Дифф только в `*.md` | PASS мгновенно, без прогонов |
| Изменить дерево после PASS | Хук отказывает по несовпадению `diffHash` |
| Убрать `frontend-ui-architecture` из `.claude/skills/` | `DEGRADED`, а не PASS |

Плюс замер: сколько прогон стоит по времени/токенам на типичном диффе. Гейт дороже минуты на
мелком диффе люди начнут обходить.

## 11. Риски

| Риск | Что делаем |
|---|---|
| Хук fail-open при падении/таймауте — гейт незаметно исчезает | Enforcement не держится на хуке (слой 3); плюс скил печатает, когда состояние нечитаемо |
| `node` недоступен в PATH хука | Только `jq`/`shasum` из `/usr/bin`; проверить реальный PATH хука однострочным пробником до реализации |
| Ложный блок | Два фильтра, только изменённые строки, закрытый каталог, обязательный escape hatch |
| Дорогой прогон | Детерминированные гейты первыми, fan-out только на больших диффах, замер из §10 |
| Карта скилов протухнет | Preflight существования + README с changelog |
| Required check на форке | Проверить доступность rulesets для этого репозитория; если недоступно — слой 3 существует как workflow, а «required» включается там, где план позволяет |

## 12. Второй проход: что добавить

Приоритет сверху вниз. Первые четыре пункта меняют решения из §1–§11, остальные их дополняют.

### 12.1 Гейт должен быть бинарным, а не трёхуровневым — правка к §7

Самый неудобный вывод. В §7 у нас три уровня, из которых блокирует только CRITICAL, а WARNING и
SUGGESTION «предупреждают». Google на данных Tricorder говорит, что это ровно тот режим, который
не работает: *«developers ignore compiler warnings»*, поэтому у них проверка либо ломает сборку,
либо подавляется — **среднего тира, который копится, не существует**.

Как примиряем с тем, что контрактная шкала продукта трёхуровневая: шкала остаётся трёхуровневой
для *findings*, но **вердикт гейта бинарный**. Каждый выпущенный finding обязан иметь ровно один
исход: исправлен, подавлен с причиной, или блокирует. «Посмотрю потом» как исход не существует —
иначе через месяц отчёт станет стеной текста, которую пролистывают.

Практически: WARNING/SUGGESTION не идут в блокирующий вердикт, но и не сыплются списком — они
уходят в markdown-секцию отчёта (см. 12.9) и не требуют действия. Блокирует только закрытый
каталог §7.2.

### 12.2 Finding без предложенного фикса не выпускается

Оттуда же: *«Anything that can be fixed automatically should be fixed automatically»* — в Google
предложенные фиксы применяются около 3000 раз в день.

Правило для скила: **если finding не может назвать конкретный следующий шаг (диff, точная правка
или ссылка на правило) — он не выпускается вообще.** Это не косметика: см. 12.3, почему непонятное
сообщение считается ложным срабатыванием даже когда баг настоящий.

### 12.3 Метрика качества — «эффективные ложные», по поведению, а не по правоте

Tricorder держит цель *«менее 10% эффективных ложных срабатываний»* при фактических «чуть ниже 5%».
Ключ — определение: срабатывание считается ложным, если **разработчик не совершил никакого действия**,
увидев его. То есть настоящий баг, описанный непонятно, статистически — ложное срабатывание.

Что добавляем в §10: гейт пишет строчку в лог на каждый прогон (вердикт, сколько CRITICAL, сколько
подавлено, был ли override). Растущая доля override и подавлений — сигнал, что гейт раскалиброван,
и это надо видеть числом, а не ощущением. Это же закрывает и гниение подавлений: периодический
аудит `pr-self-review-ignore` по возрасту.

### 12.4 Детерминированные проверки правил репозитория — новый подраздел к §7.1

Раздел «Do not touch» корневого `AGENTS.md` — готовый каталог CRITICAL, считается голым git'ом,
ноль токенов. Проверено на реальной истории:

| Проверка | Команда | Уровень |
|---|---|---|
| Пять симлинков `CLAUDE.md` целы | `git ls-files -s \| awk '$1=="120000"'` → ровно 5 строк | CRITICAL |
| Миграции только добавляются | любой `M`/`R`/`D` по `server/src/db/migrations/**/*.sql` | CRITICAL |
| Схема не поехала без миграции | `server/src/db/schema/**` в диффе, нового `migrations/*.sql` нет | CRITICAL |
| Lock-файл не правлен руками | lock в диффе без соответствующего `package.json` | CRITICAL |
| `.claude/INSIGHTS.md` на месте | не переименован, не удалён | CRITICAL |

Два нюанса, без которых правило было бы шумным, и оба найдены на истории:

- `meta/_journal.json` и `meta/*_snapshot.json` **легитимно** меняются при каждой генерации.
  Наивное «папка migrations изменена → CRITICAL» орало бы на каждую миграцию. Правило —
  только по `*.sql`.
- Коммит `2006964` («repair the migration journal») переименовал пять миграций `R100` и правил
  снапшоты, то есть сделал ровно запрещённое — и это был **осознанный ремонт** автором репозитория.
  Живое доказательство, что у каждого детерминированного правила обязан быть задокументированный
  override, иначе первый же легитимный случай научит команду обходить гейт.

Сюда же переносим из §7.2 проверку рассинхрона двух копий `vendor/shared` — она тоже
детерминированная и не требует модели.

### 12.5 Инкрементальность — обязательна, а не желательна. Правка к §4/§6

Измерено: текущая ветка против `main` — **216 файлов, 10 022 строки** (103 `client`, 84 `server`).
Оговорка из §6 «≤3 файла — ревьюим инлайн» к такому не применима, а fan-out на 216 файлов дорог
настолько, что гейт просто отключат.

- **Кэш по содержимому.** Ключ: `sha256(содержимое файла) + версия скила + версия промпта`.
  Именно по содержимому, а не по mtime — ESLint отдельно документирует `--cache-strategy content`
  как средство ровно для случая, когда время модификации меняется, а содержимое нет; git-checkout
  это он и есть.
- **Отдавать сохранённый вывод, а не только вердикт** — приём Turborepo: при попадании в кэш
  восстанавливается и терминальный вывод, поэтому попадание неотличимо от настоящего прогона.
- **Skip-when-empty** — у lefthook: если после фильтрации в бакете не осталось файлов, команда не
  запускается вовсе. У нас — не спавнить субагента на пустой бакет.

### 12.6 Размер диффа задаёт глубину ревью, а не блокировку

Google: *«100 строк обычно разумный размер, 1000 обычно слишком много»*, и отдельно —
*«изменение на 200 строк в одном файле может быть нормальным, но размазанное по 50 файлам обычно
слишком велико»*. SmartBear/Cisco: смотреть не более 200–400 строк за раз, дальше способность
находить дефекты падает.

Наши коммиты — стабильно 26–48 файлов и 600–1200 строк, ветка целиком — 216 файлов. Порог «≤400
строк» как блокировка дал бы красное почти на каждом нашем PR, то есть ровно усталость от алертов,
из-за которой гейты отключают.

Поэтому размер **не блокирует**, а переключает режим: выше порога гейт честно печатает, что ревью
неполное и уверенность ниже, и предлагает разбить. Притворяться, что 216 файлов отревьюены
одинаково внимательно, — худший вариант, чем сказать правду.

### 12.7 Секреты ищет gitleaks, а не модель

`secret_leak` в §7.2 должен производиться детерминированным сканером (regex + энтропия), а не
LLM-проходом: дешевле, воспроизводимо, без ложных «похоже на ключ». gitleaks умеет скоупиться на
дифф (`--staged` в их собственном pre-commit хуке, `--log-opts` для диапазона коммитов).

Их же escape hatch — именованный `SKIP=gitleaks` — хороший прецедент для наших подавлений: видимый
и точечный, а не глобальное выключение.

Бонус: на публичном репозитории GitHub push protection работает бесплатно и **блокирует пуш с
секретом** сам — это фактически четвёртый слой защиты, который не надо строить.

### 12.8 Один required check, без path-фильтров — правка к §4, слой 3

Ловушка подтверждена официальной документацией: *«A workflow is skipped by path filtering… Associated
checks stay in a "Pending" state and block merging»*, и совет там прямой — **не делать required
пропускаемые workflow**. У нас все пять workflow'ов path-фильтрованы, а PR, трогающий только
`.claude/**`, `docs/**` или `specs/**`, не запускает ни одного.

Решение: ровно **один** required check с именем `pr-self-review / gate`, который **никогда** не
фильтруется по путям, а фильтрацию делает внутри. Финальная job с `if: always()`, агрегирующая
`needs.*.result` и проходящая, если апстрим-джобы `skipped`. Это надёжнее, чем дублирующий
skip-workflow с тем же именем: агрегатор не может разъехаться с path-паттернами, а дубль — может.

### 12.9 Вывод, который можно использовать, а не только прочитать

- **Аннотации прямо в диффе PR.** Загрузка SARIF через `github/codeql-action/upload-sarif`
  (нужно `security-events: write`) показывает findings построчно в PR. На публичных репозиториях
  code scanning доступен; на приватных требует платной подписки.
- **Лимиты, о которые легко убиться.** У workflow-команд (`::error file=…,line=…`) потолок:
  10 аннотаций каждого типа на шаг, 50 на job, 50 на прогон, и лишние **молча отбрасываются в
  порядке появления, а не по важности**. Если идём этим путём — сортировать CRITICAL первыми и
  резать по лимиту. SARIF держит до 5000 и приоритизирует по severity сам, поэтому он основной,
  а workflow-команды — запасной путь.
- **Формат сообщений — Conventional Comments:** `issue (blocking):`, `suggestion (non-blocking):`,
  `nitpick (non-blocking):`. «Блокирующий / неблокирующий» — явная часть спецификации, и это тот же
  словарь, которым пользуются живые ревьюеры. Отдельно удобен `(if-minor)` — им кодируем полосу
  уверенности чуть ниже порога ≥8: показать, но не блокировать.
- **Отдельный markdown-канал для доказательств** (приём Danger, у которого четыре примитива:
  `fail` / `warn` / `message` / `markdown`): таблица «какие файлы куда отроутились, какие гейты
  отработали, что подавлено, какой diffHash» не должна считаться findings — это контекст, а не
  замечания.

### 12.10 Чего решили НЕ делать

- **Автофикс в гейте.** Google фиксит автоматически, но у них фикс предлагается в ревью, а не
  применяется гейтом молча. Гейт, который сам правит код перед пушем, лишает автора контроля над
  тем, что он отправляет. Finding обязан нести конкретный фикс (12.2), применяет его человек.
- **`e2e` в дефолтном прогоне.** `./scripts/e2e.sh` поднимает изолированный стек на трёх портах;
  это минуты. В локальный гейт не идёт — только в CI-слой.
- **Свой третий тир предупреждений, который копится.** См. 12.1.
