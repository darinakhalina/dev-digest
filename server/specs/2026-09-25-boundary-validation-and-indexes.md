# Spec: Zod at every entry point, one retry owner, and the missing indexes

| | |
|---|---|
| **Spec ID** | SPEC-2026-09-25-boundary-validation-and-indexes |
| **Status** | draft |
| **Source** | Phase 2 (server) of the whole-project audit of 2026-09-25, continued after
  `SPEC-2026-09-25-onion-debt-cleared` |

## Problem & why

Three more findings from the same audit pass, small enough to fold into one spec:

- One route parsed its body by hand inside the handler (`RunRequest.parse(req.body ?? {})`),
  against the house rule in `server/AGENTS.md` that says request validation happens in the route
  schema, before the handler runs, never inside it.
- A job's payload was cast (`payload as CloneJobPayload`) rather than parsed. A payload written by
  an older version of the server, or corrupted in the `jobs` table, would reach the handler as
  whatever shape it happened to have, and only fail — confusingly — wherever the first missing field
  was read.
- The OpenAI and Anthropic SDKs retry a failed call twice by default, and the adapter wraps every
  call in its own retry helper on top. For `completeStructured`, which also retries on a schema
  failure, the three layers multiply: up to 3 (schema reprompt) × 4 (adapter retry) × 3 (SDK retry)
  = 36 requests for one review.
- Five queries the server actually runs have no matching index: findings by review, reviews by PR
  and kind, PR files and commits by PR, and agent runs by workspace/PR/status.

## Goals / Non-goals

**Goals**

- Every route validates its body through the route schema; no handler calls `.parse` itself.
- A job payload is validated against a schema before its handler ever sees it, and before the job
  is even queued.
- Exactly one layer retries a failed LLM call.
- The five queries above use an index.

**Non-goals**

- Rewriting the reprompt-on-schema-failure loop in `completeStructured`. That retry is not a network
  retry; it is asking the model again after it produced output that failed grounding. It stays.
- Auditing every other route for a hand-rolled parse. Only the one instance the audit found existed.
- A general performance pass on the PR list's remaining N+1 GitHub-detail backfill. Out of scope,
  named separately in the audit's phase 2 notes.

## User stories

- As a developer running a review, I want it to cost at most a few retries when the model is
  flaky, not dozens, so that one bad response doesn't multiply into a long, expensive hang.
- As a developer replaying an old `jobs` row after a schema change, I want a clear validation error
  naming the field, not a handler crashing on `undefined.something`.

## Acceptance criteria (EARS)

- **AC-1** — WHEN `POST /pulls/:id/review` is called with no body, a body that is `null`, or a body
  matching the run-request shape, the system SHALL accept it and treat a missing body as an empty
  request, without any handler code calling a parser itself.
- **AC-2** — WHEN a job is enqueued with a payload that does not match the schema its handler was
  registered with, the system SHALL reject the enqueue call and SHALL NOT write a row for it.
- **AC-3** — The system SHALL send at most one retried attempt sequence per failed LLM network call:
  the SDK client itself SHALL NOT retry.
- **AC-4** — Querying findings by review, reviews by PR, PR files or commits by PR, or agent runs by
  workspace/PR/status SHALL use an index, not a full scan.
  _(observable: `EXPLAIN` on each of these queries against a non-trivial table shows an index scan)_

## Edge cases

| Case | Handling |
|---|---|
| A job payload that was valid under an older schema, now invalid | Enqueue fails loudly instead of the handler failing confusingly later |
| A structured-output call that fails validation on every reprompt | Still exhausts its reprompt budget (default 2 extra attempts) — unchanged, only the network-retry layer under it is thinned |
| An index on a table that starts empty | No behavioural difference; the index exists from the first row |

## Non-functional

- One new migration, generated by `pnpm db:generate` — never hand-written.
- No API-visible behaviour change other than AC-1's edge case and AC-2's earlier rejection point.

## Cross-module interactions

`JobRunner.register` (`platform/jobs.ts`) changes its signature to take a schema; both of its
current callers (`repos` and `repo-intel`) update in the same change.

## Contracts

No `@devdigest/shared` contract changes. `CloneJobPayload` and `IndexPayload`, both server-internal,
become Zod schemas instead of plain interfaces, so they can be validated as well as typed.

## Untrusted inputs

Job payloads read back from the `jobs` table are treated as untrusted at the point they are
enqueued (AC-2). This spec does not add validation when a queued row is later read back, since no
code path re-reads and re-runs a stored payload independently of the handler that already validated
it at enqueue time.
